## 一、项目定位

### 1.1 一句话定义

> **多平台电商订单同步中台** —— 让无货源卖家在**一个后台**里，完成来自多个电商平台订单的**拉取、下单、履约、回写**。

**更通俗的说法：一个"订单搬运工"。**

```
   Shopify          我们            供应商
  （平台）    ←→   （Dsers）   ←→   （1688 / 转运仓）
```

它替卖家省掉的活：

```
手工：
  看订单 → 复制买家地址 → 打开 1688 → 粘贴
  → 复制商品SKU → 粘贴 → 下单
  → 等发货 → 复制运单号 → 回 Shopify → 粘贴 → 点发货

Dsers：
  点一下按钮
```

### 1.2 对标产品

**DSers** —— AliExpress 官方合作的 Shopify 代发货（Dropshipping）管理工具。

### 1.3 边界（不做什么）

| 不做 | 原因 |
|---|---|
| ❌ 不做电商平台本身 | 本项目不卖货，只是订单的"中转站" |
| ❌ 不做 ERP（进销存/财务） | 范围过大，与核心价值无关 |
| ❌ 不做物流系统 | 只搬运运单号，不追踪物流轨迹 |
| ❌ 不做 AliExpress 代下单 | 需要企业级 ISV 资质，个人开发者无法申请 |

## 二、角色与用户

### 2.1 相关方（6 类）

1. **无货源卖家** —— 核心用户
2. 买家（最终消费者）
3. 供应商（1688 / AliExpress 上的卖家）
4. 电商平台（Shopify / WooCommerce）
5. 供应商平台（1688 / AliExpress）
6. 平台运营方（本项目自己）

### 2.2 谁才是「系统用户」★

> **相关方 ≠ 用户。** 只有需要登录的才叫用户。

| 相关方 | 是系统用户吗 | 在系统中的形态 |
|---|---|---|
| **商家** | ✅ 是 | `merchant` 表 + 登录（阶段 6） |
| 买家 | ❌ 否 | `orders` 表里的几列数据 |
| 供应商 | ❌ 否 | **一个 HTTP 接口地址** |
| 电商平台 | ❌ 否 | **一份配置（URL + Token）** |

**结论**：当前阶段只需实现**商家**一个角色。

## 三、业务流程

### 3.1 完整闭环（四步）★

```
┌──────────────────────────────────────────────────────────┐
│ ① 拉订单                                                  │
│    电商平台（Shopify）──────────→ 本系统                   │
│    触发：商家点「同步订单」                                │
│    动作：调平台 API → 转换为标准模型 → 落库                │
├──────────────────────────────────────────────────────────┤
│ ② 下单给供应商                                             │
│    本系统 ────────────────────→ 供应商                     │
│    触发：商家点「下单给供应商」                             │
│    动作：传幂等键 + 收货信息 + 商品 → 拿回供应商单号         │
│    状态：PENDING → ORDERED                                │
├──────────────────────────────────────────────────────────┤
│ ③ 查物流                                                  │
│    本系统 ────────────────────→ 供应商                     │
│    触发：商家点「同步物流」/ 轮询                          │
│    动作：用供应商单号查询 → 拿回运单号                      │
│    状态：ORDERED → SHIPPED                                │
├──────────────────────────────────────────────────────────┤
│ ④ 回写平台  ★ 闭环终点                                     │
│    本系统 ────────────────────→ 电商平台（Shopify）         │
│    触发：③ 完成后                              │
│    动作：调 Fulfillment API → Shopify 订单变「已发货」      │
│    状态：SHIPPED → SYNCED                                 │
│    结果：买家收到发货邮件，可查物流                         │
└──────────────────────────────────────────────────────────┘
```

**四步走完 = 一个订单的生命周期结束 = 完整闭环。**

### 3.2 ★ 下单 ≠ 发货，是两次独立交互

**这是最容易搞混的一点。**

| 动作 | 我们传什么 | 我们拿回什么 | 状态推进 |
|---|---|---|---|
| **② 下单** | `orders.id`（幂等键）<br>收货信息<br>商品明细 | **供应商订单号** | `PENDING` → `ORDERED` |
| **③ 查物流** | **供应商订单号** | **运单号** + 承运商 | `ORDERED` → `SHIPPED` |

**下完单那一刻货还没发，不可能有运单号。** 这是两次请求，中间可能隔好几天。

### 3.3 订单状态机

```
PENDING ──→ ORDERED ──→ SHIPPED ──→ SYNCED
已拉取      已下单       已发货       已回写
          （有供应商单号）（有运单号）（平台已更新）
```

**异常分支**（至少要有，实现可后置）：

| 异常 | 处理 | 现状 |
|---|---|---|
| 下单给供应商失败 | 状态保持 `PENDING`，记录失败原因，可重试 | ⏳ 现在直接抛 `BizException`，状态未变（天然保持 `PENDING`），但没有落「失败原因」 |
| 回写平台失败 | 状态保持 `SHIPPED`，标记 `sync_failed = 1`，定时补偿 | ❌ **未实现**。现在失败直接抛异常，`sync_failed` 字段还空着 |
| 平台订单被取消 | 本地状态 → `CANCELLED` | ⏳ 未实现（`cancelled_at` 已在 A 区同步） |

> **为什么这些可以先不做**：它们全都属于「失败之后怎么办」。
> 主干链路（成功了怎么办）没跑通之前，补偿逻辑没有存在的意义 —— **因为你不知道要为哪种失败做补偿**。
> 现在主干通了，这些是阶段 6 的活。

### 3.4 ★ 本系统状态 vs 平台状态（必须分开）

| | 本系统 `status` | 平台 `fulfillment_status` |
|---|---|---|
| 谁说了算 | **我们** | 平台 |
| 谁写 | 只有业务代码 | 同步逻辑 |
| 会变吗 | 只单向推进 | 平台说变就变 |
| 取值 | `PENDING`/`ORDERED`/`SHIPPED`/`SYNCED` | `null`/`fulfilled` |

**混用的后果**：同步逻辑会把我们推进的状态冲掉——"已下单"变回 `PENDING`，业务乱套。

**映射关系**（用于理解，不用于代码）：

| 本系统 | Shopify |
|---|---|
| `PENDING` | `financial_status: paid`, `fulfillment_status: null` |
| `SHIPPED` / `SYNCED` | `fulfillment_status: fulfilled` |

## 四、系统架构

### 4.1 分层

```
Controller   接收 HTTP 请求，参数校验
    ↓
Service      业务逻辑，事务边界
    ↓
Client/Adapter  与外部平台/供应商打交道
    ↓
Mapper       数据库访问（MyBatis-Plus）
```

### 4.2 适配器模式（阶段 6 实现）★

**设计目标**：接入一个新平台，**只需新增一个 Adapter 实现类**，Service / Controller / 数据库一行不改。

```
                    ┌─────────────────────┐
                    │  PlatformAdapter    │  ← 接口
                    │  + fetchOrders()    │
                    │  + fulfill()        │
                    └──────────┬──────────┘
                               │
              ┌────────────────┼────────────────┐
              ▼                                 ▼
    ┌──────────────────┐            ┌──────────────────┐
    │ ShopifyAdapter   │            │ WooCommerceAdapter│
    └──────────────────┘            └──────────────────┘

                    ┌─────────────────────┐
                    │  SupplierAdapter    │  ← 接口
                    │  + placeOrder()     │
                    │  + fetchTracking()  │
                    └──────────┬──────────┘
                               │
              ┌────────────────┼────────────────┐
              ▼                                 ▼
    ┌──────────────────┐            ┌──────────────────┐
    │ MockSupplier     │            │ (未来) AliExpress │
    │ (本地模拟服务)    │            │  需 ISV 资质      │
    └──────────────────┘            └──────────────────┘
```

> ⚠️ **为什么不现在就抽？**
> 现在只有一个平台。**差异看不见的时候，抽象是猜的。** 等真接 WooCommerce，知道差异在哪了再抽，抽象才有依据。
> 这不是"不会做"，是"知道现在做是错的"。

**注意**：供应商侧**已经落地了**（阶段 3），但**没有抽 `SupplierAdapter` 接口** ——
只有一个 `SupplierClient` 类直接调用模拟供应商服务。

**为什么不抽？** 和平台侧同一条道理：现在只有一个供应商，**差异看不见的时候，抽象是猜的**。
`SupplierClient` 本身已经是一个清晰的边界（只有它知道供应商接口长什么样），
等真接第二个供应商时，从它抽出接口就行，改动很小。

### 4.3 核心数据流

```
平台原始 JSON
      ↓  Converter 负责翻译（差异都在这里被吸收）
实体（PlatformOrder / OrderItem）
      ↓  Service 处理（不认识任何具体平台）
落库 / 展示 / 回写
```

## 五、数据模型 ★

### 5.1 表清单

| 表 | 作用 | 谁写 |
|---|---|---|
| `orders` | 订单主表，一单一行 | 同步逻辑 + 业务代码 |
| `order_items` | 订单明细，一商品一行 | 同步逻辑 |

**只有两张表。** 为什么不拆，见 5.5。

> 字段级详细说明（每个字段的来源、坑、用在哪）见 **《数据库设计.md》**。

### 5.2 ★ 表的三个分区（最重要的约定）

**每张表的列，按「谁写它」分三个区：**

| 区 | 列 | 谁写 | 同步逻辑能碰吗 |
|---|---|---|---|
| **A 平台镜像区** | `platform_order_id`、`order_number`、`name`、`email`、金额、`shipping_*`、`financial_status`、`fulfillment_status`、`created_at` | 同步逻辑 | ✅ 可以整块覆盖 |
| **B 自有业务区** | `status`、`supplier_order_id`、`tracking_number`、`tracking_company`、`sync_failed` | **只有业务代码** | ❌ **绝对不碰** |
| **C 本地字段区** | `id`、`create_time`、`update_time` | 数据库自动 | ❌ 不碰 |

> **写同步代码时，SQL 里只出现 A 区的列。B 区一个都别提。**
>
> **为什么这条最重要**：平台的 `fulfillment_status` 会变，同步要覆盖它；但 `status` 是我们的业务进展，已经下单了就不能被刷回 `PENDING`。

**代码层的对应约定**：`ShopifyOrderConverter` **只映射 A 区字段**。

### 5.3 ★ 幂等设计（两把锁）

| 锁 | 在哪 | 防的是什么 |
|---|---|---|
| 唯一索引 `uk_platform_order(platform, platform_order_id)` | 数据库 | **本系统内**重复插入 |
| 幂等键 `orders.id` | 传出去的参数 | **跨系统**重复下单 |

**这两把锁不能互相替代**——一个管库内，一个管库外。

#### 跨系统幂等：为什么需要它

**场景**：给供应商下单时网络超时，我们不知道对方收没收到。

- **重试** → 供应商可能收到两份 → **重复发货，真金白银的损失**
- **不重试** → 可能根本没下成功 → **漏单**

**解法**：下单时带一个幂等键（`clientOrderNo = orders.id`）。供应商那边**必须记录**它：

```sql
-- 供应商侧的表（我们看不见，但一定长这样）
CREATE TABLE supplier_orders (
    client_order_no BIGINT NOT NULL,                   -- 我们传的 orders.id
    ...
    UNIQUE KEY uk_client_order_no (client_order_no)    -- ★ 靠这个挡重
);
```

> **★ 幂等键不是一个"字段"，是「一个字段 + 一份记录」。**
> **字段负责"传"，记录负责"记"。少了记录，字段没用。**

**真实世界对应**：支付宝 / 微信支付的 `out_trade_no`。

**为什么选 `orders.id` 而不是 `order_number`？**

| 候选 | 问题 |
|---|---|
| `order_number`（`#1001`） | 平台侧编号，跨平台可能撞车；可能为空 |
| `id` | ✅ 本系统内唯一、单调递增、无业务含义、绝不为空 |

### 5.4 `orders` 表关键字段

完整结构与字段说明见《数据库设计.md》，这里只列设计要点：

| 字段 | 设计要点 |
|---|---|
| `id` | 主键 + **跨系统幂等键** |
| `platform` + `platform_order_id` | **联合唯一索引**。两列组合，因为不同平台的订单 ID 可能撞车 |
| `order_number` / `name` | 都给人看。⚠️ `name` 是 `#1001`，**不是收货人姓名** |
| `shipping_*`（8列） | 下单给供应商的核心数据。前缀预留（将来有 `billing_*`） |
| `shipping_country_code` | 用代码（`CA`）不用名字（`Canada`）——代码更可靠 |
| `status` | **本系统状态机**，只由业务代码写 |
| `fulfillment_status` | **平台侧状态**，同步逻辑写。⚠️ 和 `status` 无关 |
| `supplier_order_id` | 下单后写入。**③查物流时用它当查询键** |
| `tracking_number` / `tracking_company` | ④回写时传给平台 |
| `created_at` vs `create_time` | 前者是买家下单时间，后者是我们入库时间。**可能差很久** |

### 5.5 `order_items` 表关键字段

| 字段 | 设计要点 |
|---|---|
| `order_id` | 关联 `orders.id`（本系统主键），**不是 `platform_order_id`** |
| `sku` | 商家自定义编码。⚠️ **可能为 null**（实测 3 条里 2 条为空） |
| `variant_id` | 平台侧变体 ID，**比 `sku` 可靠**。②认规格用 |
| `platform_line_item_id` | 平台侧明细行 ID。★ **④回写时必须用它**，平台不认我们的自增 `id` |
| `variant_title` | 规格名（`150cm` / `Red / L`）。展示用 |
| `quantity` | ②下单数量 + ④回写数量 |
| `price` | **单价**，不是小计。存原始数据，不存计算结果 |

**读取商品的优先级**：`sku` → `variant_id` → `platform_line_item_id`

### 5.6 关于「不拆表」的决策 ★

**曾考虑过的方案**（Shopify 官方 AI 助手的建议）：

```
platform_orders / platform_order_items     ← 平台镜像
supplier_orders / supplier_order_items     ← 供应商侧
shipments                                  ← 物流（支持多包裹）
product_mappings                           ← SKU 映射
```

**结论：方向对，但现在不做。**

**理由：**

1. **`supplier_orders` 的字段只能靠猜。** 还没见过任何真实的供应商 API。凭空想象对方的字段，**接真接口时基本要重做**。
2. **拆分的前提是"两侧的数据开始打架"。** 现在只有一个供应商、一次发货，还没到打架的时候。
3. **改表很便宜，没数据很贵。** `ALTER TABLE` 一分钟，类名 IDEA 一键重命名，代码有 Git 兜底。**唯一改不了的是「没数据、没跑通的流程」。**

**正确时机：见过真实供应商 API 之后再拆。** 那时知道对方要什么、给什么。

**记录在案，等时机到了再实施**（见《数据库设计.md》第六章「说好不做的」）。

## 六、外部平台对接要点 ★

**这一章是实战踩坑记录。** Shopify 的文档不会告诉你这些。

### 6.1 ★ PII 限制：地址数据会被静默抹掉

**症状**：API 正常返回，但 `shipping_address` 只有 4 个字段，`email` / `phone` 全是 `null`。

**根因**：Shopify 对客户隐私数据（姓名、地址、邮箱、电话）有**套餐门槛**。

> **非开发者店铺 / 低套餐店铺，API 返回的 PII 会被静默抹掉——不报错，就是没有。**

**GraphQL 会明确报错：**

```
This app is not approved to access the Customer object.
Access to personally identifiable information (PII) like customer names,
addresses, emails, phone numbers is only available on Shopify,
Advanced, and Plus plans.
```

**解决**：换成**开发者店铺**（套餐 `Advanced App Development`），PII 全部拿到。

| | 老店铺 | 新店铺 |
|---|---|---|
| 域名 | `learnapi-x3jri7fj` | `hope-qymbdz6y` |
| 套餐 | 低套餐 | `Advanced App Development` |
| 地址 | ❌ 只有 4 个字段 | ✅ 完整 15 个字段 |

### 6.2 ★ 排查数据缺失的方法论

**数据不对时，先怀疑源头，再怀疑代码。**

```text
① curl 绕过自己的代码，直接拉原始 JSON
   → 证明源头给的是全的还是缺的
② 如果 REST 看起来"正常但数据少"，改用 GraphQL 再查一次
   → GraphQL 报错，REST 静默脱敏
③ 确认源头没问题，再回头查自己的 DTO 接没接住
```

### 6.3 踩坑清单

| # | 坑 | 说明 |
|---|---|---|
| 1 | **`status=any` 必须传** | 默认只返回 `status=open`，**归档订单静默漏掉**。订单发货后常被自动归档 |
| 2 | **草稿订单不在 `/orders.json`** | 后台点「创建订单」默认是 **Draft Order**，必须点**「标记为已付款」**才变正式订单 |
| 3 | **`shipping_address.name` 可能是空串** | 实测 #1003 是 `""`。兜底用 `billing_address.name` |
| 4 | **商品标识可能为空** | #1001 的 `sku` 和 `variant_id` **都是 null** |
| 5 | **金额是字符串** | `"664.95"` 不是数字，要用 `BigDecimal` 转 |
| 6 | **时间带时区** | `2026-09-06T12:34:56-04:00`，用 `OffsetDateTime.parse()` |

### 6.4 实际数据结构（已确认）

**Shopify 返回 92 个顶层字段。**

| 我们接收 | 数量 | 说明 |
|---|---|---|
| `orders` 顶层 | 12 | 订单号、金额、状态、时间 |
| `shipping_address` | 10 | 姓名、电话、地址、城市、邮编、省、国家代码等 |
| `billing_address` | 1 | **仅用于姓名兜底** |
| `line_items` | 8 | 商品名、规格、数量、单价、各种 ID |

**其余的不接，因为闭环用不到**（够用原则）。

> **数字订正说明**：本表在 v3.0 里写的是「88 个顶层字段 / 订单顶层 21 个 / shipping_address 8 个」，
> 是凭印象估的。v4.0 按实际拉下来的 JSON 逐个数过，改成上表的数字。

**阶段 4 新增的接收点**：`GET /orders/{id}/fulfillment_orders.json` 返回的履约单列表，
**只接 `id` 和 `status` 两个字段**（对方返回 30 多个）。见 `dto/FulfillmentOrderListResponse.java`。

## 九、已知限制与应对

| 限制 | 应对方案 |
|---|---|
| 国内平台（淘宝/京东/拼多多）需要企业资质 | 不接入 |
| AliExpress 代下单需要 ISV 资质 | **用本地模拟供应商服务代替** |
| 个人无法成为服务商 | 项目定位为「平台侧中台」，聚焦上游 |
| Shopify PII 有套餐门槛 | 已换开发者店铺，数据完整 |

**关于供应商侧的处理：**

> 供应商在架构上就是**一个适配器**（`SupplierAdapter`）。我们用本地模拟服务实现它，**换成真实平台只需替换实现类**，其余代码不动。
>
> 这不是"做不到"，是"个人开发者拿不到资质，所以用等价的方式验证架构"。
