> 本文档随项目演进更新。任何设计变更先改本文档，再改代码。

---

## 一、项目定位

### 1.1 一句话定义

> **多平台电商订单同步中台** —— 让无货源卖家在**一个后台**里，完成来自多个电商平台订单的**拉取、统一处理、状态回写**。

### 1.2 对标产品

**DSers** —— AliExpress 官方合作的 Shopify 代发货（Dropshipping）管理工具。

它解决的核心问题是：无货源卖家原本要在 Shopify 和 AliExpress 之间**手动来回 6 步**，DSers 把它压缩成 **1 次点击**。

### 1.3 边界（不做什么）★

划清边界和确定范围一样重要，答辩时能体现工程判断力。

| 不做 | 原因 |
|---|---|
| ❌ 不做电商平台本身 | 本项目不卖货，只是订单的"中转站" |
| ❌ 不做 ERP（进销存/财务） | 范围过大，与核心价值无关 |
| ❌ 不做物流系统 | 只搬运运单号，不追踪物流轨迹 |
| ❌ 不做 AliExpress 代下单 | 需要企业级 ISV 资质，个人开发者无法申请 |

## 二、角色与用户

### 2.1 相关方（6 类）

1. **无货源卖家** —— 核心付费用户
2. 买家（最终消费者）
3. 供应商（AliExpress / 1688 上的卖家）
4. 电商平台（Shopify / WooCommerce）
5. 供应商平台（AliExpress）
6. 平台运营方（本项目自己）

### 2.2 谁才是「系统用户」★

> **相关方 ≠ 用户。** 只有需要登录的才叫用户。

| 相关方 | 是系统用户吗 | 在系统中的形态 |
|---|---|---|
| **商家** | ✅ 是 | `merchant` 表 + 登录 |
| **平台管理员** | ✅ 是（远期） | 内部后台 |
| 买家 | ❌ 否 | `orders` 表里的几列数据 |
| 供应商 | ❌ 否 | 一个 HTTP 接口地址 |
| 电商平台 | ❌ 否 | 一份配置（URL + Token） |

**结论**：当前阶段只需实现**商家**一个角色。

## 三、业务流程

### 3.1 完整闭环（五幕）★

```
【第一幕】拉取
    电商平台（Shopify）──────────→ 本系统
    触发：商家点击「同步订单」/ 定时任务
    动作：调平台 API 拉订单 → 转换为标准订单模型 → 落库
    
【第二幕】展示
    本系统 ──────────────────────→ 商家浏览器
    触发：商家打开订单列表
    动作：返回所有平台的订单，统一视图

【第三幕】处理
    商家 ────────────────────────→ 本系统
    触发：商家勾选订单，点「下单给供应商」
    动作：调供应商适配器下单 → 本地状态改为「已下单」
    
【第四幕】履约
    供应商 ──────────────────────→ 本系统
    触发：供应商发货（模拟服务主动推送 / 本系统轮询）
    动作：拿到运单号 → 本地状态改为「已发货」
    
【第五幕】回写
    本系统 ──────────────────────→ 电商平台（Shopify）
    触发：第四幕完成后自动触发
    动作：调平台 Fulfillment API → Shopify 订单变「已发货」
    结果：买家收到发货邮件，可查物流
```

**五幕走完 = 一个订单的生命周期结束 = 完整闭环。**

### 3.2 订单状态机

```
                  ┌──────────────┐
                  │  待处理       │  PENDING
                  │  (订单已入库)  │
                  └──────┬───────┘
                         │ 商家点「下单给供应商」
                         ▼
                  ┌──────────────┐
                  │  已下单       │  ORDERED
                  │  (供应商已受理) │
                  └──────┬───────┘
                         │ 供应商发货，拿到运单号
                         ▼
                  ┌──────────────┐
                  │  已发货       │  SHIPPED
                  │  (本地有运单号) │
                  └──────┬───────┘
                         │ 回写平台成功
                         ▼
                  ┌──────────────┐
                  │  已同步       │  SYNCED
                  │  (平台已更新)  │
                  └──────────────┘
```

**异常分支**（至少要有，实现可后置）：

| 异常 | 处理 |
|---|---|
| 下单给供应商失败 | 状态保持 PENDING，记录失败原因，可重试 |
| 回写平台失败 | 状态保持 SHIPPED，标记 `sync_failed`，定时补偿 |
| 平台订单被取消 | 本地状态 → CANCELLED |

### 3.3 与平台状态的映射

本系统状态是**自己的**，平台状态是**平台的**，两者要能互译：

| 本系统 | Shopify | WooCommerce |
|---|---|---|
| PENDING | `financial_status: paid`<br>`fulfillment_status: null` | `status: processing` |
| SHIPPED / SYNCED | `fulfillment_status: fulfilled` | `status: completed` |

## 四、系统架构

### 4.1 分层

```
Controller   接收 HTTP 请求，参数校验
    ↓
Service      业务逻辑，事务边界
    ↓
Adapter      与外部平台/供应商打交道  ★ 核心抽象
    ↓
Mapper       数据库访问（MyBatis-Plus）
```

### 4.2 适配器模式 ★

**这是整个项目的架构核心，也是答辩的亮点。**

```
                    ┌─────────────────────┐
                    │  PlatformAdapter    │  ← 接口
                    │  ─────────────────  │
                    │  + fetchOrders()    │
                    │  + fulfill()        │
                    └──────────┬──────────┘
                               │
              ┌────────────────┼────────────────┐
              ▼                                 ▼
    ┌──────────────────┐            ┌──────────────────┐
    │ ShopifyAdapter   │            │ WooCommerceAdapter│
    │ (真实对接)        │            │ (真实对接)         │
    └──────────────────┘            └──────────────────┘
```

```
                    ┌─────────────────────┐
                    │  SupplierAdapter    │  ← 接口
                    │  ─────────────────  │
                    │  + placeOrder()     │
                    │  + fetchTracking()  │
                    └──────────┬──────────┘
                               │
              ┌────────────────┼────────────────┐
              ▼                                 ▼
    ┌──────────────────┐            ┌──────────────────┐
    │ MockSupplier     │            │ (未来)AliExpress   │
    │ (本地模拟服务)    │            │  需 ISV 资质       │
    └──────────────────┘            └──────────────────┘
```

**设计目标**：接入一个新平台，**只需新增一个 Adapter 实现类**，Service / Controller / 数据库一行不改。

### 4.3 核心数据流

```
平台原始 JSON
      ↓  Adapter 负责翻译（差异都在这里被吸收）
标准订单模型（StandardOrder）
      ↓  Service 处理（不认识任何具体平台）
落库 / 展示 / 回写
```

## 五、数据模型

### 5.1 现状（v1）

| 表 | 说明 |
|---|---|
| `shopify_order` | 订单主表，含 `shopify_order_id`、`order_number` 等 |
| `order_items` | 订单明细，通过 `order_id` 关联主表自增 `id` |

**已知问题**：表名和字段名把平台名称写死了，无法容纳第二个平台。

### 5.2 目标结构（v2）

**订单主表 `orders`**（由 `shopify_order` 改造）

| 字段 | 变化 | 说明 |
|---|---|---|
| `id` | 保留 | 主键 |
| `platform` | **新增** | `SHOPIFY` / `WOOCOMMERCE`，标识来源 |
| `platform_order_id` | **改名** | 原 `shopify_order_id`，平台侧的订单 ID |
| `order_number` | 保留 | 平台展示用订单号 |
| `merchant_id` | **新增（远期）** | 多租户隔离 |
| `status` | **新增** | 本系统状态机：PENDING / ORDERED / SHIPPED / SYNCED |
| `tracking_number` | **新增** | 运单号 |
| `tracking_company` | **新增** | 物流公司 |
| `supplier_order_id` | **新增** | 供应商侧单号 |
| `sync_failed` | **新增** | 回写平台是否失败 |
| 其余平台字段 | 保留 | 金额、状态、时间等 |

**唯一索引调整**：`uk_platform_order`（`platform` + `platform_order_id`）

**明细表 `order_items`** —— 结构基本不变，仅表名规范化。

**新增表 `supplier_orders`**（供应商单）

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `order_id` | 关联本系统订单 |
| `supplier` | 供应商标识 |
| `supplier_order_no` | 供应商侧单号 |
| `status` | 供应商侧状态 |
| `tracking_number` | 运单号 |
| `created_at` | 下单时间 |

## 八、已知限制与应对 ★

| 限制 | 应对方案 |
|---|---|
| 国内平台（淘宝/京东/拼多多/抖店）需要企业资质 | 不接入，答辩时说明行业规则 |
| AliExpress 代下单需要 ISV 资质 | 用本地模拟供应商服务代替 |
| 个人无法成为服务商 | 项目定位为「平台侧中台」，聚焦上游 |

**答辩标准话术**：

> "DSers 采用 ISV 服务商模式，需要企业资质才能获得 AliExpress 的接口权限。我作为个人开发者无法申请，因此项目聚焦在**平台侧的中台能力**——真实的多平台订单拉取、统一处理与状态回写。供应商侧通过本地服务模拟，**架构上它就是一个适配器，换成真实平台只需替换实现类**。"

## 附：本阶段演示目标

**能演出一条完整闭环，中间不断点：**

```
打开后台 → 看到多平台订单 → 点「下单给供应商」
→ 供应商侧收到并发货 → 系统抓回运单号
→ 回写 Shopify → 打开 Shopify 后台，订单真的变成「已发货」
```

**最高潮的一幕**：打开 Shopify 后台，亲眼看到状态被改了。
