## 阶段 2 · 数据补全 ← 你现在在这

**目标**：把 Shopify 给的完整数据接住，让订单「能拿去下单」。

### 为什么要做这一步

闭环的第二步是「下单给供应商」。下单要告诉供应商：**寄给谁、寄到哪、电话多少**。

**这些数据 Shopify 早就给了**（实测返回完整的加拿大地址），但我们的 DTO 里没接，Jackson 解析时**直接丢掉了**。

**同时**，商品明细里缺 `variant_id` / `platform_line_item_id`：

- 缺 `variant_id` → 认不出买家买的是哪个规格（`sku` 实测有三条里两条为空）
- 缺 `platform_line_item_id` → 阶段 4 回写发货时，无法告诉 Shopify "发的是哪几行"

### 步骤

| 步 | 做什么 | 文件 |
|---|---|---|
| 2.1 | 新建 `ShippingAddressDto`（对应 JSON 的 `shipping_address` 对象） | `dto/` |
| 2.2 | 新建 `BillingAddressDto`（兜底取姓名用） | `dto/` |
| 2.3 | `ShopifyOrderDto` 补地址字段 + 关联两个地址对象 | `dto/` |
| 2.4 | `OrderItemDTO` 补 `platform_line_item_id` / `variant_id` / `product_id` / `variant_title` / `variant_title` | `dto/` |
| 2.5 | `PlatformOrder` 实体补 8 个 `shipping*` 字段 | `entity/` |
| 2.6 | `OrderItem` 实体补 4 个字段 | `entity/` |
| 2.7 | **新建 `ShopifyOrderConverter`**：手写映射（弃用 `BeanUtils`） | `converter/` |
| 2.8 | `OrderService.saveOrder()` 改用 Converter | `service/` |
| 2.9 | **修 `ShopifyClient`**：URL 加 `?status=any&limit=250` | `client/` |
| 2.10 | 清空旧数据，重新同步 3 单 | 验证 |

### 为什么手写 Converter 而不用 `BeanUtils` ★

`BeanUtils.copyProperties()` 只按**同名**拷贝。而我们两边字段名大量不同：

| DTO | 实体 | 要做什么 |
|---|---|---|
| `id` | `platformOrderId` | 改名 |
| `totalPrice`（String） | `totalPrice`（BigDecimal） | 类型转换 |
| `createdAt`（String） | `createdAt`（LocalDateTime） | 类型转换 |
| `shippingAddress.name` | `shippingName` | **拆嵌套对象** |
| — | `platform` / `status` | 常量赋值 |

**大部分字段都要特殊处理，那不如全手写**——一眼能看出哪个字段从哪来，出错好定位。

## 阶段 3 · 业务动作：供应商下单 ✅ 已完成

**目标**：能真实地把订单"发出去"，状态推进。

### 步骤

| 步 | 做什么 | 说明 |
|---|---|---|
| 3.1 | 定义 `SupplierAdapter` 接口 | `placeOrder()` / `fetchTracking()` |
| 3.2 | 新建模拟供应商服务（独立 Spring Boot，端口 8081） | **真实在跑的服务** |
| 3.3 | 模拟服务提供 `POST /api/orders`（接单） | 返回 `supplierOrderNo` |
| 3.4 | 模拟服务提供 `POST /api/orders/{no}/ship`（发货） | 生成运单号 |
| 3.5 | 写 `MockSupplierAdapter` 调用模拟服务 | RestTemplate |
| 3.6 | 新增接口 `POST /orders/{id}/place-order` | 触发下单 |
| 3.7 | 下单成功 → `status` → `ORDERED`，写入 `supplier_order_id` | 状态推进 |

### 关键设计点

**① 参数用专门的请求 DTO，不传实体**

新建 `SupplierOrderRequest`。

> **实体是"我们的形状"，请求类是"对方需要什么"。** 传实体等于把内部结构暴露给对方。

**② 幂等键传 `orders.id`**

供应商侧必须**记录**这个键（`client_order_no` 上有唯一索引），才能挡住重复下单。

> **幂等键不是一个"字段"，是「一个字段 + 一份记录」。字段负责"传"，记录负责"记"。**

**③ 返回值要能区分三种情况**

| 情况 | 含义 |
|---|---|
| 成功 | 拿到供应商单号 |
| 明确失败 | 对方说不行，可以重试或放弃 |
| **超时** | **什么都不知道**——最危险，不能盲目重试 |

返回 `null` 或 `boolean` 都无法区分第 3 种。**用结果对象（`code` / `msg` / `data`）。**

### 验收标准

- 模拟服务日志里能看到真实的请求
- 订单状态 `PENDING` → `ORDERED`
- `supplier_order_id` 有值

**预计**：2-3 天

### ✅ 实际实现（2026-10-01）

| 计划 | 实际 | 原因 |
|---|---|---|
| 定义 `SupplierAdapter` **接口** + `MockSupplierAdapter` 实现 | 只写了 `SupplierClient` 一个类，**没抽接口** | 现在只有一个供应商。**差异看不见的时候，抽象是猜的** —— 和 Converter 同一条道理。等真接第二个供应商时再抽 |
| `POST /api/orders`、`POST /api/orders/{no}/ship` | `POST /supplier/orders`、`POST /supplier/orders/{id}/ship` | 路径统一加 `/supplier` 前缀，一眼看出这是给外部系统用的 |
| 只需「接单 + 发货」两个端点 | 多了一个 **`GET /supplier/orders/{id}`** | 阶段 3 要查物流，必须有个查询端点。**这个端点是阶段 4 的伏笔** |
| 新增 `POST /orders/{id}/place-order` | 实际是 **`POST /orders/{id}/place`** | 更短 |

**多出来的一件事：发货端点是幂等的。**
重复调 `/ship` 不会生成第二个运单号，而是把原来那个还给你。理由和下单一样 ——
**对方要的是「结果」，不是「异常」**。

## 阶段 4 · 闭环收口：发货回写平台 ★★★ ✅ 已完成

**目标**：**这是整个项目的核心。**

### 步骤

| 步 | 做什么 | 说明 |
|---|---|---|
| 4.1 | 摸清 Shopify Fulfillment API 的两步流程 | |
| 4.2 | **先用 Postman 手动调通，再写代码** | ⚠️ 别直接写 Java |
| 4.3 | `fetchTracking()` 抓回运单号 → `status` → `SHIPPED` | |
| 4.4 | `fulfill()` 实现回写 | |
| 4.5 | 回写成功 → `status` → `SYNCED` | ★ 闭环完成 |
| 4.6 | 回写失败 → `sync_failed = 1` | 预留补偿 |
| 4.7 | 新增接口 `POST /orders/{id}/sync-tracking` | 手动触发 |

### 关键设计点

**Shopify 发货是两步接口：**

```text
① GET  /orders/{platform_order_id}/fulfillment_orders
       → 拿 fulfillment_order_id

② POST /fulfillments.json
       body: {
         "fulfillment": {
           "line_items_by_fulfillment_order": [{
             "fulfillment_order_id": <上一步拿到的>,
             "fulfillment_order_line_items": [
               { "id": <platform_line_item_id>, "quantity": 2 }
             ]
           }],
           "tracking_number": "xxx",
           "tracking_company": "FedEx",
           "notify_customer": true
         }
       }
```

⚠️ **明细行用 `platform_line_item_id`，不是我们的自增 `id`。**

⚠️ 带 `notify_customer: true`，买家会收到发货邮件——**演示效果好**。

### 验收标准 ★

> **打开 Shopify 后台，那个订单从「未发货」变成「已发货」，运单号在里面。**

**这一步通了，项目就成了。**

**预计**：3-5 天

### ✅ 实际实现（2026-10-02）—— 项目已经成了

**验收标准已达成**：Shopify 后台的 #1004、#1003 两条订单，`fulfillment_status` 从 `null` 变成了 **`fulfilled`**，
并且各自挂着一条真实的履约记录（可在 `/orders/{id}/fulfillments.json` 查到，含运单号和承运商）。

#### 和计划不一致的地方（★ 以实际为准）

| 计划 | 实际 | 说明 |
|---|---|---|
| body 里平铺 `"tracking_number"` / `"tracking_company"` | **嵌套在 `tracking_info` 里**：`{"tracking_info": {"number": ..., "company": ...}}` | 计划里那个格式是**猜的**，实测不被接受。**这就是「先用 Postman 手动调通再写代码」的价值** |
| `"notify_customer": true`（演示效果好） | **`false`** | 这是真实店铺，测试期间**不能打扰真实买家**。毕设演示时可以改回 `true` |
| `POST /orders/{id}/sync-tracking` | **`POST /orders/{id}/push-tracking`** | 命名统一成「推」（我们主动推给平台），和 `refresh-shipping`（拉）对照 |
| 4.6「回写失败 → `sync_failed = 1`」 | ❌ **没实现** | 现在失败是直接抛异常。`sync_failed` 字段还空着，留给阶段 6 的补偿机制 |

#### 多出来的三件事（计划里没想到）

1. **`PlatformOrderMapper.updateSynced`** —— 第四个手写 SQL，只改 `status` 一列。
   计划里没提这个方法的必要性：回写成功后状态要推进到 `SYNCED`，而 `updateShipped` 只写运单号那三列，管不了这一步。
2. **一个新 DTO：`FulfillmentOrderListResponse`** —— 承接 `/fulfillment_orders.json` 的响应。
   **只声明了 `id` 和 `status` 两个字段**，Shopify 返回的另外 30 多个一个都没接（够用原则的又一次应用）。
3. **履约 API 需要单独申请权限** —— 读订单正常 ≠ 能读履约单。
   必须额外开 `read_merchant_managed_fulfillment_orders`、`write_merchant_managed_fulfillment_orders`、
   `read_fulfillments`、`write_fulfillments` 这四个，否则报 `The api_client does not have the required permission(s).`
   （**加完权限后 token 不变**，容易误以为没生效）

#### 四个防御分支都验证过

| 场景 | 结果 |
|---|---|
| `status ≠ SHIPPED` 就回写 | 400 拦住（含重复回写：第二次调是 `SYNCED`，同样被拦） |
| 订单不存在 | 404 |
| Shopify 没返回 `fulfillment_order_id` | 500 |
