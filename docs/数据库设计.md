## 一、两条必须记住的规则

### 规则 1 · 分区：谁写的字段，谁负责

每张表的列，按「谁写它」分三个区：

| 区 | 列 | 谁写 |
|---|---|---|
| **A 平台镜像区** | `platform_order_id`、`order_number`、金额、`shipping_*`、`fulfillment_status`… | **同步逻辑**写，每次同步可以整块覆盖 |
| **B 自有业务区** | `status`、`supplier_order_id`、`tracking_number`、`tracking_company`、`sync_failed` | **只有业务代码写，同步逻辑永远不碰** |
| **C 本地字段区** | `create_time`、`update_time`、`id` | 数据库自动维护 |

**★ 为什么这条最重要：**

平台返回的 `fulfillment_status` 会变（买家退款、平台改单），同步逻辑必须覆盖它。

但 `status`（我们的状态机）**不能被覆盖**。已经下单给供应商了，不能因为下一次同步把它刷回 `PENDING`。

> **写同步代码时，SQL 里只出现 A 区的列。B 区的列一个都别提。**

### 规则 2 · 幂等：两把锁，锁的是两件事

| 锁 | 在哪 | 防的是什么 |
|---|---|---|
| 唯一索引 `uk_platform_order(platform, platform_order_id)` | 数据库 | **本系统内**重复插入 |
| 幂等键 `orders.id` | 传出去的参数 | **跨系统**重复下单 |

**这两把锁不能互相替代**，一个管库内，一个管库外。

## 二、`orders` 表（订单主表）

### 2.1 完整结构

```sql
CREATE TABLE `orders` (
  -- ===== 识别一单 =====
  `id`                     bigint        NOT NULL AUTO_INCREMENT COMMENT '主键',
  `platform`               varchar(20)   NOT NULL DEFAULT 'SHOPIFY'  COMMENT '来源平台',
  `platform_order_id`      bigint        NOT NULL COMMENT '平台侧订单ID',
  `order_number`           varchar(50)   NOT NULL COMMENT '订单号',
  `name`                   varchar(50)   NOT NULL COMMENT '订单显示名',

  -- ===== 买家信息 =====
  `email`                  varchar(100)  DEFAULT NULL COMMENT '买家邮箱',

  -- ===== 金额 =====
  `total_price`            decimal(10,2) DEFAULT NULL COMMENT '订单总金额',
  `subtotal_price`         decimal(10,2) DEFAULT NULL COMMENT '商品小计',
  `total_tax`              decimal(10,2) DEFAULT NULL COMMENT '税费',
  `currency`               varchar(10)   DEFAULT 'USD' COMMENT '币种',

  -- ===== 收货地址 =====
  `shipping_name`          varchar(100)  DEFAULT NULL COMMENT '收件人姓名',
  `shipping_phone`         varchar(50)   DEFAULT NULL COMMENT '收件人电话',
  `shipping_address1`      varchar(200)  DEFAULT NULL COMMENT '收货地址1，如街道',
  `shipping_address2`      varchar(200)  DEFAULT NULL COMMENT '收货地址2，如门牌',
  `shipping_city`          varchar(100)  DEFAULT NULL COMMENT '城市',
  `shipping_zip`           varchar(20)   DEFAULT NULL COMMENT '邮编',
  `shipping_province`      varchar(100)  DEFAULT NULL COMMENT '省/州',
  `shipping_country_code`  varchar(10)   DEFAULT NULL COMMENT '国家代码，如 CA',

  -- ===== 平台侧状态 =====
  `financial_status`       varchar(20)   DEFAULT NULL COMMENT '支付状态',
  `fulfillment_status`     varchar(20)   DEFAULT NULL COMMENT '发货状态',

  -- ===== 平台侧时间 =====
  `created_at`             datetime      DEFAULT NULL COMMENT '平台下单时间',
  `cancelled_at`           datetime      DEFAULT NULL COMMENT '取消时间',

  -- ===== 本地系统字段 =====
  `create_time`            datetime      DEFAULT CURRENT_TIMESTAMP COMMENT '本地创建时间',
  `update_time`            datetime      DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '本地更新时间',

  -- ===== 自有业务状态 ★ =====
  `status`                 varchar(20)   NOT NULL DEFAULT 'PENDING' COMMENT '订单状态',
  `supplier_order_id`      varchar(100)  DEFAULT NULL COMMENT '供应商订单号',
  `tracking_number`        varchar(100)  DEFAULT NULL COMMENT '运单号',
  `tracking_company`       varchar(50)   DEFAULT NULL COMMENT '承运商',
  `sync_failed`            tinyint       DEFAULT '0' COMMENT '回写是否失败：0否 1是',

  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_platform_order` (`platform`,`platform_order_id`),
  KEY `idx_order_number` (`order_number`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单主表（多平台）';
```

### 2.2 字段逐个说明

#### ▌ `id` ★★★ — 本系统主键，也是跨系统幂等键

| | |
|---|---|
| **是什么** | 数据库自增主键 |
| **谁生成** | 我们（数据库） |
| **什么时候用** | **②下单给供应商时，当 `clientOrderNo` 传出去** |

**为什么它能当幂等键：** 本系统内唯一、单调递增、无业务含义、绝不为空。

**★ 它的真正作用（一定要理解）：**

给供应商下单时，如果网络超时，我们不知道对方收没收到。重试可能下两单（重复发货，真金白银的损失），不重试可能漏单。

**解法**：下单时带上 `id` 当幂等键。供应商那边**必须记录**它：

```sql
-- 供应商侧的表（我们看不见，但一定长这样）
CREATE TABLE supplier_orders (
    client_order_no BIGINT NOT NULL,                   -- 我们传的 orders.id
    ...
    UNIQUE KEY uk_client_order_no (client_order_no)    -- ★ 靠这个挡重
);
```

> **幂等键不是一个"字段"，是「一个字段 + 一份记录」。**
> **字段负责"传"，记录负责"记"。少了记录，字段没用。**

**真实世界对应**：支付宝/微信支付的 `out_trade_no`。

---

#### ▌ `platform` + `platform_order_id` ★★★ — 平台是谁、哪一单

| 字段 | 是什么 | 谁生成 |
|---|---|---|
| `platform` | 来源平台，当前恒为 `SHOPIFY` | 我们（写死） |
| `platform_order_id` | **Shopify 侧的订单 ID**（JSON 里的 `id`，如 `5678901234567`） | Shopify |

**什么时候用：④回写发货时用它定位平台订单。**

**★ 和 `id` 的区别（最容易混的一对）：**

| | `id` | `platform_order_id` |
|---|---|---|
| 谁生成 | 我们的库 | Shopify |
| 唯一范围 | 只在本系统内 | 只在 Shopify 内 |
| 用途 | **传给供应商当幂等键** | **回写时定位平台订单** |

**一个订单，`id` 可能是 `3`，`platform_order_id` 可能是 `5678901234567`。两个都要存。**

**为什么要两列一起做唯一索引？**
因为接第二个平台时，不同平台的订单 ID 可能撞车。单列唯一索引会把另一个平台的订单误判成"重复"挡在门外。

---

#### ▌ `order_number` / `name` — 别混，都是给人看的

| 字段 | 示例值 | 说明 |
|---|---|---|
| `order_number` | `#1001` | 平台展示的订单号 |
| `name` | `#1001` | 订单显示名。⚠️ **不是收货人姓名！** |

> ⚠️ **踩过的坑**：一开始以为 `name` 是收货人姓名，实际它是 `#1001` 这种订单显示名。
> **收货人姓名在 `shipping_name`。**

**这两个字段只用于展示，接口调用不用它们。**

---

#### ▌ `email` — 买家邮箱

来源：Shopify 顶层字段 `email`（不是地址对象里的）。

**什么时候用**：某些供应商下单时需要邮箱发通知。

---

#### ▌ `shipping_*` 8 个字段 ★★★ — 下单给供应商的核心数据

| 字段 | 来源（Shopify JSON） | 示例 |
|---|---|---|
| `shipping_name` | `shipping_address.name` | `Russell Winfield` |
| `shipping_phone` | `shipping_address.phone` | `+14165550135` |
| `shipping_address1` | `shipping_address.address1` | `105 Victoria St` |
| `shipping_address2` | `shipping_address.address2` | 门牌/单元，可为 null |
| `shipping_city` | `shipping_address.city` | `Toronto` |
| `shipping_zip` | `shipping_address.zip` | `M5C1N7` |
| `shipping_province` | `shipping_address.province` | 省/州，可能为 null |
| `shipping_country_code` | `shipping_address.country_code` | `CA` |

**什么时候用：②下单给供应商——把这一组装进请求发给供应商。没有这组数据，订单一单都发不出去。**

**★ 三个必须知道的坑：**

**坑 1：`shipping_name` 可能是空字符串！**

实测 #1003 的 `shipping_address.name` 是 `""`，但 `billing_address.name` 是 `"Russell Winfield"`。

**转换时要兜底**：
```text
shipping_name 取值优先级：
  1. shipping_address.name（非空才用）
  2. billing_address.name（兜底）
  3. shipping_address.first_name + last_name（再兜底）
```

**坑 2：老店铺（低套餐）这些字段全是 null。**

Shopify 对 PII（客户姓名/地址/邮箱/电话）有套餐限制。**低套餐店铺的 API 会静默抹掉这些数据，不报错。** 我们已换成开发者店铺（`Advanced App Development`），数据完整。

> **排查数据缺失的经验**：用 GraphQL 查——**REST 静默脱敏，GraphQL 会明确报错。**

**坑 3：为什么用 `country_code`（`CA`）不用 `country`（`Canada`）？**

代码比名字可靠：不受大小写、空格、翻译影响。传供应商时更保险。

**为什么全部加 `shipping_` 前缀？**
Shopify 同时给 `shipping_address` 和 `billing_address`。现在只用收货地址，**预留前缀**，将来加账单地址不冲突。

---

#### ▌ `financial_status` / `fulfillment_status` — 平台说了算

| 字段 | 含义 | 常见值 |
|---|---|---|
| `financial_status` | 平台侧**支付**状态 | `PAID` / `pending` / `refunded` |
| `fulfillment_status` | 平台侧**发货**状态 | `null`（未发货）/ `fulfilled`（已发货） |

**这两个是 Shopify 给的事实，会变。同步逻辑负责覆盖它们。**

---

#### ▌ `status` ★★★ — 我们自己的状态机

```
PENDING（已拉取）──→ ORDERED（已下单）──→ SHIPPED（已发货）──→ SYNCED（已回写）
```

| 值 | 含义 | 什么时候推进到它 |
|---|---|---|
| `PENDING` | 已从平台拉取，等待处理 | 同步订单时写入初始值 |
| `ORDERED` | 已向供应商下单 | 下单成功、拿到 `supplier_order_id` |
| `SHIPPED` | 供应商已发货、已拿到运单号 | 查到 `tracking_number` |
| `SYNCED` | 运单号已回写到平台 | Shopify 回写成功 |

**★ `status` 和 `fulfillment_status` 完全无关，别混：**

| | `status` | `fulfillment_status` |
|---|---|---|
| 谁说了算 | **我们** | 平台 |
| 谁写 | 只有业务代码 | 同步逻辑 |
| 会变吗 | 只单向推进 | 平台说变就变 |

> **混用的后果**：如果写同步逻辑时用 `fulfillment_status` 去更新 `status`，就会把已经"已下单"的订单刷回 `PENDING`——业务乱套。

---

#### ▌ `supplier_order_id` ★★★ — 供应商侧的订单号

| | |
|---|---|
| **是什么** | 下单成功后，**供应商返回给我们的**订单号 |
| **谁生成** | 供应商 |
| **谁来写** | 我们的业务代码（阶段 3） |
| **什么时候用** | **③查物流时，用它当查询键** |

**★ 关键：查物流要用 `supplier_order_id`，不是用我们的 `id`。**

因为问供应商"我的单发货了吗"，它只认自己发出去的那个号。

---

#### ▌ `tracking_number` / `tracking_company` ★★★ — 运单号

| 字段 | 说明 |
|---|---|
| `tracking_number` | 运单号，供应商发货后拿到 |
| `tracking_company` | 承运商，如 `FedEx`、`USPS` |

**什么时候用：④回写发货时，把这两个传给 Shopify。**

---

#### ▌ `sync_failed` — 回写失败的标记

`0` = 正常，`1` = 回写平台时失败了。

**用途**：失败时不阻塞流程，先记标记。后续可以写个定时任务扫 `sync_failed = 1` 的订单重试。

---

#### ▌ 时间字段：两组，别混 ★

| 字段 | 含义 | 谁写 |
|---|---|---|
| `created_at` | **平台侧业务时间**——买家真正下单那一刻 | 同步逻辑 |
| `cancelled_at` | 平台侧取消时刻 | 同步逻辑 |
| `create_time` | **入库时间**——这行数据写进我们库的时刻 | 数据库自动 |
| `update_time` | 本行最后修改时刻 | 数据库自动 |

> **两者可能差很久。** 买家 9-01 下单，我们 9-20 才同步进来：`created_at` = 9-01，`create_time` = 9-20。
>
> **统计"本月订单量"要用 `created_at`，用 `create_time` 会算错。**

---

#### ▌ 金额字段

| 字段 | 说明 |
|---|---|
| `total_price` | 总额 = 商品小计 + 运费 + 税费 − 折扣 |
| `subtotal_price` | 商品小计（不含运费税费） |
| `total_tax` | 税费合计 |
| `currency` | 币种，如 `USD` |

**★ 坑：平台返回的金额是字符串**（`"664.95"`），入库前必须 `new BigDecimal(str)`。

**不能用 `double`** —— 浮点数做金额会丢精度（`0.1 + 0.2 = 0.30000000000000004`）。

**转之前先判 null**，否则 `new BigDecimal(null)` 会抛异常。

---

### 2.3 索引

| 索引 | 作用 |
|---|---|
| `PRIMARY KEY (id)` | 按 ID 查订单（详情、下单） |
| `uk_platform_order (platform, platform_order_id)` | ★ 幂等第一道闸门，**数据库层防重复** |
| `idx_order_number (order_number)` | 预留：将来到货按订单号搜索 |

## 三、`order_items` 表（订单明细）

### 3.1 完整结构

```sql
CREATE TABLE `order_items` (
  `id`                     bigint        NOT NULL AUTO_INCREMENT COMMENT '主键',
  `order_id`               bigint        NOT NULL COMMENT '所属订单id，关联 orders.id',

  `title`                  varchar(200)  NOT NULL COMMENT '商品名称',
  `platform_line_item_id`  bigint        DEFAULT NULL COMMENT '平台侧明细行ID',
  `variant_id`             bigint        DEFAULT NULL COMMENT '平台侧变体ID',
  `product_id`             bigint        DEFAULT NULL COMMENT '平台侧商品ID',
  `variant_title`          varchar(200)  DEFAULT NULL COMMENT '规格名称，如150cm',
  `sku`                    varchar(50)   DEFAULT NULL COMMENT '商品编码',

  `quantity`               int           NOT NULL COMMENT '购买数量',
  `price`                  decimal(10,2) NOT NULL COMMENT '单价',

  `create_time`            datetime      DEFAULT CURRENT_TIMESTAMP COMMENT '本地创建时间',
  `update_time`            datetime      DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '本地更新时间',

  PRIMARY KEY (`id`),
  KEY `idx_order_id` (`order_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单明细表';
```

### 3.2 字段逐个说明

#### ▌ `order_id` — 关联字段

关联 **`orders.id`**（本系统主键），**不是 `platform_order_id`**。

用本系统主键关联，业务查询就永远不用碰平台标识。

---

#### ▌ 商品标识三件套 ★★★ — 认得出买家买的是哪个

**平台给的商品标识有三个，哪个都不保证一定有值：**

| 字段 | 可靠性 | 说明 |
|---|---|---|
| `sku` | ⚠️ **可能为 null** | 商家自定义编码。**实测 #1001 的 `sku` 就是 null** |
| `variant_id` | ✅ 一般有值 | 平台侧**变体 ID**，即"具体规格"的身份证号 |
| `platform_line_item_id` | ✅ 一定有 | 平台侧**明细行 ID** |

**读取优先级**：`sku` → `variant_id` → `platform_line_item_id`

**实测数据（三条测试订单）：**

| 订单 | 商品 | `sku` | `variant_id` |
|---|---|---|---|
| #1003 | The Complete Snowboard | `null` | `41664172818490` |
| #1002 | The 3p Fulfilled Snowboard | `sku-hosted-1` | `41664173178938` |
| #1001 | Custom Snowboard | `null` | **`null`** ⚠️ 两个都空 |

> **结论：只存 `sku` 是不够的。** 三条里有两条 `sku` 为空——如果只靠 `sku` 认商品，一半的单认不出来。

---

#### ▌ `platform_line_item_id` ★★★ — 回写发货的硬需求

**这是阶段 4 的生命线。**

回写发货时，Shopify 要求你说明「这一单里**哪几行**发货了、**各发几件**」。它认的就是 `platform_line_item_id`，**不认我们的自增 `id`**：

```json
"fulfillment_order_line_items": [
  { "id": <platform_line_item_id>, "quantity": 2 }
]
```

**少了它，回写就写不出去。**

---

#### ▌ `variant_title` — 规格名

示例值：`150cm`、`Red / L`、`Default Title`。

**展示用。** 没有它，卖家只看到商品名，不知道买家选的是哪个规格。

---

#### ▌ `quantity` / `price` — 数量和单价

| 字段 | 说明 |
|---|---|
| `quantity` | 购买数量。**回写给平台时必须传** |
| `price` | **单价**，不是小计 |

**为什么存单价不存小计？**
单价是平台给的**原始数据**，小计是**计算结果**。存原始数据，将来算折扣逻辑变了不用改数据；存计算结果，一旦算错就得回炉。

---

#### ▌ `title` — 商品名

如 `The Complete Snowboard`。`NOT NULL`，Shopify 一定给。

---

### 3.3 索引

| 索引 | 作用 |
|---|---|
| `PRIMARY KEY (id)` | 按明细 ID 查 |
| `idx_order_id (order_id)` | ★ 按订单查明细，列表页和详情页每次都用 |

> **注意**：`order_id` 上**没加外键约束**。外键会带来插入顺序限制和额外锁开销，生产环境常见做法是**只用索引、应用层保证一致性**。

## 四、闭环数据流 ★★★

**这是全文最重要的一章。写每一段业务代码前，先来看这张图。**

```text
┌──────────────────────────────────────────────────────────────────┐
│ ① 拉订单    Shopify ──→ orders / order_items                      │
├──────────────────────────────────────────────────────────────────┤
│  写 orders（A区）：                                                │
│    platform, platform_order_id, order_number, name, email,        │
│    total_price, subtotal_price, total_tax, currency,              │
│    shipping_name, shipping_phone, shipping_address1,              │
│    shipping_address2, shipping_city, shipping_zip,                │
│    shipping_province, shipping_country_code,                      │
│    financial_status, fulfillment_status, created_at, cancelled_at │
│  写 orders（B区）：status = 'PENDING'  ← 只写这一次                │
│  写 order_items：title, platform_line_item_id, variant_id,        │
│    product_id, variant_title, sku, quantity, price                │
└──────────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────────┐
│ ② 下单给供应商    我们 ──→ 供应商                                  │
├──────────────────────────────────────────────────────────────────┤
│  读 orders    ：id（幂等键）、shipping_*（8个）、email            │
│  读 order_items：title、variant_id、variant_title、quantity、sku  │
│  写 orders    ：supplier_order_id  ← 供应商返回                    │
│  状态：PENDING ──→ ORDERED                                        │
└──────────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────────┐
│ ③ 查物流          我们 ──→ 供应商                                  │
├──────────────────────────────────────────────────────────────────┤
│  读 orders：supplier_order_id   ← 用它当查询键                     │
│  写 orders：tracking_number、tracking_company                     │
│  状态：ORDERED ──→ SHIPPED                                        │
└──────────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────────┐
│ ④ 回写平台        我们 ──→ Shopify                    ★ 闭环终点   │
├──────────────────────────────────────────────────────────────────┤
│  读 orders     ：platform_order_id、tracking_number、             │
│                  tracking_company                                 │
│  写 orders     ：status = 'SYNCED'                                │
│                  （sync_failed 是预留的失败标记位，暂未使用）      │
│  状态：SHIPPED ──→ SYNCED                                         │
│  ★ 外部效果：Shopify 后台该订单显示「已发货」，运单号在里面        │
└──────────────────────────────────────────────────────────────────┘
```

**闭环的验收标准：**

> **打开 Shopify 后台，那个订单从「未发货」变成了「已发货」，运单号在里面。**

## 五、写代码时的注意事项

### 5.1 同步逻辑（阶段 1 重做）

| 事项 | 说明 |
|---|---|
| **只写 A 区** | 更新已有订单时，只更新 A 区的列。**`status`、`supplier_order_id`、`tracking_*` 一个都别提** |
| **初始状态只在插入时写** | `status = 'PENDING'` 只在 `INSERT` 时设置，`UPDATE` 时不动它 |
| **URL 要带 `status=any`** | `/orders.json` 默认只返回 `status=open`，**归档订单会静默漏掉**。必须加 `?status=any&limit=250`（✅ 已修） |
| **金额转 BigDecimal** | 转之前判 null，否则 NPE |
| **时间转 LocalDateTime** | Shopify 给的是 ISO 格式（`2026-09-06T12:34:56-04:00`），用 `OffsetDateTime.parse()` 再转 |
| **地址判空兜底** | `shipping_name` 空 → 用 `billing_address.name` |
| **幂等判断条件要和唯一索引一致** | 查重用 `platform + platform_order_id`，别只用 `platform_order_id` |

### 5.2 转换代码（DTO → 实体）

**手写转换，别用 `BeanUtils.copyProperties()`。**

原因：`BeanUtils` 只按**同名**拷贝。而我们两边的字段名大量不同：

| DTO | 实体 | 需要额外处理 |
|---|---|---|
| `id` | `platform_order_id` | 改名 |
| `totalPrice`（String） | `totalPrice`（BigDecimal） | 类型转换 |
| `createdAt`（String） | `createdAt`（LocalDateTime） | 类型转换 |
| `shippingAddress.name`（嵌套对象） | `shippingName`（扁平） | **拆对象** |
| — | `platform` | 常量赋值 |
| — | `status` | 常量赋值 |

**`BeanUtils` 只能拷贝 `title`、`sku`、`quantity` 这几个同名的，其余的都得手写。既然大部分要手写，不如全手写——一眼能看出哪个字段从哪来。**

**建议**：新建 `ShopifyOrderConverter` 类，提供两个方法：

```java
PlatformOrder toEntity(ShopifyOrderDto dto);          // 主表
OrderItem toItemEntity(OrderItemDTO dto, Long orderId); // 明细
```

### 5.3 供应商交互（阶段 3）✅ 已实现

**代码**：`client/SupplierClient.java` + `OrderService.placeOrder()` / `refreshShipping()`

| 事项 | 说明 |
|---|---|
| **幂等键传 `orders.id`** | 不是 `platform_order_id`，不是 `order_number` |
| **参数用专门的 DTO** | `SupplierOrderRequest`，**不传实体**。实体是"我们的形状"，请求类是"对方需要什么" |
| **返回值要能区分三种情况** | ① 成功 ② 明确失败 ③ **超时（什么都不知道）** —— 用 `R` 的 `code`/`msg`/`data` 承载 |
| **下单 ≠ 发货** | 是两次独立请求。下单拿 `supplier_order_id`，查物流才拿 `tracking_number` |

**实测补充的两条**：

| 事项 | 说明 |
|---|---|
| **「还没发货」不是错误** | 查物流时供货商回 `RECEIVED`，要**正常返回**（200 + 灰字提示），不是抛异常。真实场景里轮询十次可能十次都是这个回答 |
| **状态校验放最前面** | `placeOrder` 要求 `status = PENDING`、`refreshShipping` 要求 `status = ORDERED`、`pushTracking` 要求 `status = SHIPPED`。**不满足就抛 `BizException(400)`** —— 这是「三道防线」的第二道 |

### 5.4 回写平台（阶段 4）✅ 已实现

**代码**：`client/ShopifyClient.fetchFulfillmentOrderId()` / `createFulfillment()` + `OrderService.pushTracking()`

| 事项 | 说明 |
|---|---|
| **先用 curl 调通再写 Java** | ✅ 做过了，**这一条救了命**（见下面的格式修正） |
| **两步接口** | ① `GET /orders/{platform_order_id}/fulfillment_orders.json` 拿 `fulfillment_order_id`<br>② `POST /fulfillments.json` 带 ID + 运单号 |
| **权限要单独开** | 读订单正常 **≠** 能读履约单。需要 `read/write_merchant_managed_fulfillment_orders` + `read/write_fulfillments` |

**⚠️ 三处和原计划不符的（以实测为准）**：

| 原以为 | 实际 | 说明 |
|---|---|---|
| body 里平铺 `"tracking_number"` + `"tracking_company"` | 嵌套在 **`tracking_info`** 里：<br>`{"tracking_info": {"number": ..., "company": ...}}` | 平铺格式**不被接受**。这就是「先手动调通再写代码」的价值 |
| `notify_customer: true` | **`false`** | 真实店铺测试期间不能打扰真实买家。毕设演示时可以改回 `true` |
| 明细行要传 `platform_line_item_id` + `quantity` | `line_items_by_fulfillment_order` 里**只给 `fulfillment_order_id`**，不指定明细行 | 不指定 = 整单全部履约。我们的场景一单一次发完，够用 |

**没做的事**（留给阶段 6）：

| 计划 | 现状 |
|---|---|
| 回写失败置 `sync_failed = 1` | ❌ 没实现。失败直接抛异常，`sync_failed` 还空着 |
| 多包裹 / 部分发货 | ❌ 现在只取第一张 `fulfillment_order` |
| 远程成功、本地写库失败的补偿 | ❌ 靠人工重试 |

## 七、为什么这么设计（防止你改错）

### 7.1 为什么 `status` 和 `fulfillment_status` 要分开？

一个是**我们的业务进展**，一个是**平台告诉我们的事实**。

混用的后果：同步逻辑会把我们推进的状态冲掉，"已下单"变回 `PENDING`。

### 7.2 为什么唯一索引是两列组合？

不同平台的订单 ID 可能撞车。加上 `platform`，唯一性范围才正确。

### 7.3 为什么金额用 `decimal` 不用 `double`？

浮点数无法精确表示小数，做金额累加会产生误差。金融计算必须用 `decimal`（Java 里是 `BigDecimal`）。

### 7.4 为什么 `sku` 和 `variant_id` 都存？

可靠性不同，互为兜底。实测三条订单里两条 `sku` 为空。

### 7.5 为什么 `order_id` 不加外键？

外键带来插入顺序限制和额外锁开销。生产环境常见做法是只用索引、应用层保证一致性。

### 7.6 为什么不拆表？

**改表很便宜，没数据很贵。**

`ALTER TABLE` 一分钟，类名 IDEA 一键重命名，代码有 Git 兜底。

**唯一改不了的是「没数据、没跑通的流程」。**

### 8.2 状态机

```
PENDING ──→ ORDERED ──→ SHIPPED ──→ SYNCED
 拉取完成    下单成功    拿到运单号   回写成功
```

### 8.3 容易混的三对

| 别混 | 区别 |
|---|---|
| `id` vs `platform_order_id` | 我们的 vs 平台的 |
| `status` vs `fulfillment_status` | 我们的进展 vs 平台的事实 |
| `create_time` vs `created_at` | 入库时间 vs 买家下单时间 |
